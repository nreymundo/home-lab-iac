# Ansible

Configures what Terraform provisions, plus independently managed hosts:
Proxmox hosts, VMs, LXC containers, single board computers, and the K3s
cluster.

Playbooks select hosts and compose the reusable roles under `roles/`.
Inventory variables select fleet policy; role defaults describe the available
options. Start with the playbook for the operation you intend to perform.

## Choose a playbook

Paths below are relative to `playbooks/`. Host and application playbooks can
manage overlapping concerns; they are separate entrypoints, not a sequence
that should all be run on every host.

| Playbook | Target group | Purpose and prerequisites |
|----------|--------------|---------------------------|
| `ubuntu.yml` | `ubuntu_hosts` by default | Ubuntu 24.04/26.04 host setup, hardware, power, and selected optional tools. Requires working SSH/sudo access; run before K3s enrollment. See the [Ubuntu guide](../docs/ubuntu-host-provisioning.md). |
| `fedora.yml` | `fedora` | Common host setup, SSH hardening, and optional Homebrew on Fedora. |
| `rpi.yml` | `rpi` | Common host setup, SSH hardening, and selected Homebrew/Docker tools on Raspberry Pi hosts. |
| `proxmox.yml` | `proxmox` | Proxmox host configuration followed by common setup and SSH hardening. See the [Proxmox role](roles/proxmox/README.md). |
| `proxmox-fix-thin-provisioning.yml` | `proxmox` | Runs the Proxmox role with ZFS thin-provisioning enforcement enabled; it is not limited to ZFS tasks unless tags select them. |
| `public_vps.yml` | `public_vps` | Common setup and selected Docker installation. Initial SSH/UFW/fail2ban hardening belongs to Terraform cloud-init. Requires the local inventory overlay. |
| `development.yml` | `development_vms` | Development workstation tools and services. Refreshes an existing HashiCorp key before common APT tasks; see below. |
| `hermes.yml` | `hermes_vms` | Native Hermes installation and services with the VM's host setup and tools. |
| `omniroute.yml` | `omniroute_vms` | OmniRoute/Redis deployment and API reconciliation. Requires the [documented secrets and deployment prerequisites](roles/containers/omniroute/README.md). |
| `netbird.yml` | `netbird` | NetBird stack and identity bootstrap. Requires its inventory host and [SOPS secrets](secrets/README.md#netbird). |
| `garage_lxc.yml` | `garage_lxc` | LXC hardening/bootstrap and Garage installation. Requires a manually supplied Garage configuration. |
| `emqx_lxc.yml` | `emqx_lxc` | LXC hardening/bootstrap and the playbook's pinned EMQX package. |
| `photon_lxc.yml` | `photon_lxc` | LXC hardening/bootstrap, Docker, and Photon. |
| `zigbee2mqtt_lxc.yml` | `zigbee2mqtt_lxc` | LXC hardening/bootstrap, Docker, and Zigbee2MQTT. |
| `llm_lxc.yml` | `llm_lxc` | GPU LXC runtimes and applications. Requires the passed-through devices and application data/secrets. The `llama_cpp_update` play is opt-in via its tag. |
| `k3s_bootstrap.yml` | `k3s_server` | Explicitly initialize a fresh cluster on `k3s_bootstrap_host`, then join the remaining selected servers. Rejects existing datastore state. |
| `k3s_cluster.yml` | `k3s_server` | Join or reconcile selected servers against an existing cluster using `k3s_admin_host`; it does not implicitly initialize a new cluster. |
| `k3s_upgrade.yml` | `k3s_server` | Upgrade selected servers sequentially through the shared K3s workflow. |

Use the [K3s provisioning guide](../docs/k3s-provisioning.md) for host/storage
prerequisites, host selection, and cluster operations. Reconciliation and
upgrades each use one serial play with health gates; bootstrap uses separate
initialization and joining plays. A K3s no-op does not drain or restart a node.
For a complete recovery, follow the
[cluster rebuild runbook](../docs/kubernetes-bootstrap.md).

## Inventory and configuration ownership

`ansible.cfg` loads the entire `inventories/` directory and resolves roles from
`roles/`, `roles/containers/`, and `roles/vms/`.

- Inventory files bearing `DYNAMICALLY GENERATED BY TERRAFORM` are generated
  host identities. Change their owning Terraform root, not the output file.
- `baremetal.yml` supplies manually managed hosts. `all-vms.yml`, `ubuntu.yml`,
  and `k3s-cluster.yml` assemble groups without taking over generated identities.
- `public-vps.yml` is the tracked group structure; public host connection details
  come from the ignored `public-vps.local.yml` overlay.
- `inventories/group_vars/` and `inventories/host_vars/` are hand-maintained
  fleet and host policy. Keep policy at its existing level when changing it;
  child groups and host overrides affect the effective values.
- Role defaults, tasks, templates, files, and handlers own implementation.
  Keep app-specific inputs in the corresponding inventory variables.
- See [secrets/README.md](secrets/README.md) for Ansible-owned SOPS material.
  Shared Authentik credentials and cluster identity retain their documented
  Kubernetes owners. SSH-key discovery uses 1Password when explicit keys are
  not supplied.

Passing `-i` replaces the configured inventory source. Use the whole directory
when you need the aggregate groups; a generated host file alone does not
include the group hierarchy from its siblings.

## Run and validate

Commands here run from the repository root. Preserve the config context with
`ANSIBLE_CONFIG=ansible/ansible.cfg`; when working inside `ansible/`, Ansible
loads that file automatically. Check controller tools with
`scripts/bootstrap-host-tools.sh --check` and follow
[CONTRIBUTING.md](../CONTRIBUTING.md) for setup and local checks.

For example, inspect the Ubuntu target set and syntax before a host operation:

```bash
ANSIBLE_CONFIG=ansible/ansible.cfg ansible-inventory --graph ubuntu_hosts
ANSIBLE_CONFIG=ansible/ansible.cfg ansible-playbook ansible/playbooks/ubuntu.yml --limit <host> --list-hosts
ANSIBLE_CONFIG=ansible/ansible.cfg ansible-playbook ansible/playbooks/ubuntu.yml --syntax-check
```

For an intended live run, use the selected playbook's guide and limit the hosts.
`--check` connects to targets and may execute read-only probes; tasks explicitly
skipped in check mode are not validated by it. Narrow tags can depend on an
earlier full run.

Offline validation is available through the existing lint and test suite:

```bash
ANSIBLE_CONFIG=ansible/ansible.cfg ansible-lint --project-dir ansible ansible/playbooks/ ansible/roles/
python -m unittest discover -s ansible/tests -v
```

See [tests/README.md](tests/README.md) for fixture coverage and controller
prerequisites, and [AGENTS.md](AGENTS.md) for editing rules.

## Reruns and feature switches

An unchanged checkout does not guarantee a change-free run: enabled package
upgrades, image pulls, and upstream release discovery can pick up new versions.
Keep the operation's update policy in mind when rerunning a playbook.

| Concern | Current ownership and rerun behavior |
|---------|---------------------------------------|
| Homebrew | `homebrew_install_enabled: false` skips management; it does not uninstall Homebrew. Enabled runs install it when absent and ensure selected formulae are present. |
| Docker | `docker_install_enabled: false` skips management; it does not remove an existing engine or containers. |
| Swap | `swapfile_enabled: false` skips swapfile provisioning; it does not remove active swap. New K3s enrollment separately disables swap. |
| Cockpit | Disabling it removes previously role-managed access/packages; an installation never managed by the role is left alone. See the [role guide](roles/cockpit/README.md). |
| Host power | Backend `none` relinquishes managed policy; kernel values may persist until reboot. See the [role guide](roles/host_power/README.md). |
| Garage | Ansible installs the binary and unit; `/etc/garage.toml` is manually supplied. The role can select newer releases within its configured major version. |
| llama-swap | Ansible creates the model configuration only when absent; later edits remain manual. Runs resolve the latest stable binary release. See the [role guide](roles/llama_swap/README.md). |
| llama.cpp / whisper.cpp | Source updates are opt-in; build markers also detect relevant build-setting changes. See [LLM runtime](roles/llm_runtime/README.md) and [Whisper runtime](roles/whisper_runtime/README.md). |
| OmniRoute | Managed API declarations are reconciled on reruns; existing key values and native OAuth state are preserved. See the [role guide](roles/containers/omniroute/README.md). |

Other feature switches retain their role-specific semantics. Inspect the role's
defaults and tasks rather than assuming `false` means uninstall or cleanup.

## Role task organization

The larger roles use role-local task files, imported in execution order from
`tasks/main.yml`:

| Role | Task files |
|------|------------|
| `llm_runtime` | `preflight`, `packages`, `source`, `build`, `validation` |
| `hermes` | `install-prerequisites`, `identity`, `install`, `default-gateway`, `named-profiles`, `dashboard` |
| `netbird` | `secrets`, `networking`, `deployment`, `verification` |
| `omniroute` | `secrets`, `deployment`, `api-bootstrap` |

These use static `ansible.builtin.import_tasks` so existing tasks remain
visible to `--list-tasks` and selectable through `--start-at-task`, with
their original ordering, conditions, tags, and handler notifications.
Templates and handlers remain owned by their existing roles.

Homebrew keeps OS-specific prerequisites in `os-debian.yml` and `os-fedora.yml`;
both import the shared `bootstrap.yml` before formula installation. Its outer
OS selection remains dynamic.

Static helpers belong in role-local `files/`; templated configuration belongs
in `templates/`. OmniRoute's `files/bootstrap_omniroute.py` is copied unchanged
and consumes the separately rendered `templates/bootstrap-config.json.j2`.

## Development workstation repository keys

The development playbook refreshes the HashiCorp signing key before the
`common` role's APT operations when its repository source is already
configured. This lets existing hosts recover from upstream signing-key
rotations without failing before the development role runs. Fresh hosts
still configure the repository through the development role.

`roles/development_workstation/tasks/hashicorp-key.yml` downloads the official
key into the existing root-owned staging directory, converts it there, and
copies the result to the configured keyring only when its contents differ.
Download or conversion failures leave the installed keyring untouched.
The repository URL, suite, `signed-by` path, and APT signature checks remain
unchanged.

Check mode skips key download, conversion, and installation; use a normal
`playbooks/development.yml` run to repair an outdated keyring.
