# Layered Impact Check

This repo is a four-layer provisioning chain with strict source-of-truth
boundaries. Symptoms often surface one layer downstream of the real cause. This
skill assesses and reports the chain; it does not duplicate the Terraform,
Ansible, Packer, or Kubernetes implementation workflow owned by the matching
skill.

```
Packer template  ──►  Terraform root  ──►  Ansible inventory/roles  ──►  Kubernetes/Flux
(packer/)             (terraform/)        (ansible/)                    (kubernetes/)
```

Each layer has an `AGENTS.md` that defines its source-of-truth contract. Always
read the relevant subtree `AGENTS.md` before claiming an impact assessment.

## When to use

- A change to a Packer template, Terraform module/root, Ansible role/playbook,
  or generated inventory.
- Node topology changes (labels, hostnames, users, node count).
- A Terraform root with `ansible_inventory.tf`, or any diff in an inventory file
  carrying the `THIS FILE IS DYNAMICALLY GENERATED BY TERRAFORM` header.
- "Fix this Ansible failure" / "fix this Terraform plan" without checking the
  upstream source.
- Reviewing a PR that touches more than one layer.

## Inputs

- The changed path(s) (from `git diff`, a PR, or the user's description).
- Whether the change is meant to be Git-only validation or includes live ops.

## Assessment procedure

1. Read the nearest subtree `AGENTS.md` for every affected layer and identify
   the source-of-truth owner before suggesting an edit.
2. For a Terraform-backed host, trace the root's `ansible_inventory.tf` and
   `local_file` target to the generated inventory. For an inventory path, check
   the header first; redirect edits on generated files to the owning Terraform
   root.
3. Inspect the generated inventory diff after the approved Terraform generation
   step. Confirm hostnames, addresses, users, labels, groups, and topology
   changed only as intended.
4. Validate downstream Ansible assumptions by inspecting the affected
   `playbooks/`, `roles/`, `group_vars/`, and `host_vars/`, then use
   `ansible-inventory --graph` and the relevant playbook `--syntax-check`.
5. When a Packer template is involved, enumerate every Terraform root that
   clones its template name and check image, cloud-init, disk, user, and
   bootstrap compatibility before treating the change as local.
6. Return the impact and validation chain, but hand implementation to the
   layer-specific skill (`terraform-infrastructure-change`,
   `ansible-role-playbook-change`, or the applicable Packer/Kubernetes skill).

## Impact matrix

Map each changed path to its source-of-truth owner, then walk downstream. For a
Terraform root, follow `ansible_inventory.tf` and its `local_file` output to the
exact generated inventory before assessing Ansible impact. Inspect the generated
diff, then validate the playbooks, group variables, host variables, and group
assumptions that consume it. A generated file is evidence of the root output,
not an edit target.

| Changed in | Likely downstream impact | Verify |
|---|---|---|
| `packer/<template>/` | Terraform roots that clone this template; cloud-init, disks, users, image, and node bring-up compatibility | `packer validate`; inspect every Terraform root that references the template name and re-check its generated inventory/Ansible consumers |
| `terraform/modules/`, `terraform/instances/`, `terraform/cloud/` | Root-owned generated `ansible/inventories/*`, host labels, users, topology assumptions consumed by Ansible roles and K3s playbooks | `terraform fmt/validate/plan`; inspect the generated inventory diff; validate affected playbook and group assumptions |
| `ansible/roles/`, `ansible/playbooks/` | K3s cluster state, host configuration, cluster assumptions Flux then builds on | `ansible-lint`, `--syntax-check`, `--check` on reachable hosts |
| `ansible/inventories/*` | Mixed-source. Files with the `DYNAMICALLY GENERATED BY TERRAFORM` header (currently `k3s-nodes.yml`, `hermes.yml`, `llm.yml`, `garage.yml`, and `photon.yml`) are Terraform-owned — trace `ansible_inventory.tf` and fix upstream. The remaining host inventories (`all-vms.yml`, `baremetal.yml`, `k3s-cluster.yml`, `public-vps.yml`) and all `group_vars/` / `host_vars/` are hand-maintained — edit directly. | Check the header, trace the owning Terraform root, inspect the generated diff, and validate downstream groups/playbooks |
| `kubernetes/infrastructure/` | `kubernetes/clusters/production/ks/*.yaml` ordering/inclusion; SOPS secrets; services that depend on it | `kubectl kustomize kubernetes/infrastructure`; `flux get kustomizations` |
| `kubernetes/components/` | All workloads that reference the component (search before assuming local) | `kubectl kustomize` on representative consumers |
| `kubernetes/clusters/production/ks/` | Reconciliation order and rendered inventory (`prune: true` deletes removed objects) | `kubectl kustomize kubernetes/clusters/production/ks`; `flux get kustomizations` |

## Layer validation commands

Run only the ones matching changed layers. `plan`, `--check`, and live flux
reconciliation need credentials/hosts and may be live ops.

```bash
# Packer
TEMPLATE=packer/<template>
packer init "$TEMPLATE"
packer fmt -check -recursive "$TEMPLATE"
packer validate "$TEMPLATE"

# Terraform (per modified root, including cloud roots)
ROOT=terraform/instances/vm/k3s_nodes   # or terraform/instances/lxc/... or terraform/cloud/...
terraform -chdir="$ROOT" init
terraform -chdir="$ROOT" fmt -check
terraform -chdir="$ROOT" validate
terraform -chdir="$ROOT" plan    # requires backend + provider creds; live
# After the approved generation step, inspect the root-owned output:
git diff -- ansible/inventories/<generated-inventory>.yml

# Ansible
ANSIBLE_CONFIG=ansible/ansible.cfg ansible-lint ansible/playbooks/ ansible/roles/
ANSIBLE_CONFIG=ansible/ansible.cfg ansible-inventory \
  -i ansible/inventories/<generated-inventory>.yml --graph
ANSIBLE_CONFIG=ansible/ansible.cfg ansible-playbook ansible/playbooks/<playbook>.yml --syntax-check
# With reachable target hosts only:
ANSIBLE_CONFIG=ansible/ansible.cfg ansible-playbook ansible/playbooks/<playbook>.yml --check

# Kubernetes
kubectl kustomize --load-restrictor=LoadRestrictionsNone <changed-path> >/dev/null
scripts/kubeconform.sh
flux get kustomizations
flux get helmreleases -A
```

## Output to produce

For each proposed change, return:

1. **Source-of-truth owner** of each changed path (which subtree `AGENTS.md`).
2. **Generated-output trace** when applicable: Terraform root,
   `ansible_inventory.tf`, exact inventory file, and the inspected diff.
3. **Downstream consumers** that must be checked (concrete playbooks, roles,
   group variables, and group assumptions).
4. **Validation chain** to run, clearly labelled read-only vs live.
5. Any **manual live step** required that the Git change alone cannot cover
   (e.g. `terraform plan`, `ansible-playbook --check`,
   `flux reconcile kustomization flux-system --with-source`).
6. Any Packer template compatibility checks when a Terraform root clones one.
7. Whether the change **should be refused or redirected upstream** (e.g. a
   hand-edit to Terraform-generated inventory).

## Anti-patterns to call out

- Hand-editing a Terraform-generated file under `ansible/inventories/`
  (the ones with the `DYNAMICALLY GENERATED BY TERRAFORM` header). Note that
  `group_vars/`, `host_vars/`, and the hand-maintained host inventories are
  editable directly — check the header.
- Skipping the generated inventory diff or accepting a changed host group,
  label, user, or topology without checking the consuming playbooks and group
  variables.
- Encoding a topology fix in Ansible when the real source is Terraform.
- Treating a Packer base-template change as local; downstream Terraform consumers
  that clone it must be re-checked.
- Repeating Terraform implementation or Ansible role design in this assessment;
  hand those edits to the layer-specific skill.
- Treating a `kubernetes/components/` change as local; all referencing consumers
  must be inspected.
- Validating with `kubectl apply` when `kubectl --dry-run=client` or
  `flux get` answers the question.
